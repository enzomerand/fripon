# Fripon

Browser extension (Chrome desktop, Safari macOS, Firefox bonus) that flags dropshipped
(Shein, Temu, AliExpress…) and overpriced Vinted listings. Free, open source, AGPL-3.0.
Design: `docs/superpowers/specs/2026-10-20-fripon-extension-design.md`. Mockups: `docs/mockups/`.

## Commands

- `npm run dev` (Chrome, watch) / `npm run dev:firefox`; `npm run build` -> `.output/chrome-mv3`; `npm run zip`.
- Load by hand: `chrome://extensions` -> Developer mode -> "Load unpacked" -> `.output/chrome-mv3`.
- Safari (macOS only): `npm run build:safari` -> `.output/safari-mv3`; `npm run safari:sync` copies it into the Xcode project; `npm run safari:app` = both + `xcodebuild` Debug, ad-hoc signed -> `.output/safari-xcode/Build/Products/Debug/Fripon.app`. Steps to load it in Safari are in `docs/safari.md`.
- `npm run check` = `format:check` + `lint` + `typecheck` + `test` (the local gate, run it before every commit). It covers `server/` too: Prettier and ESLint see it, `typecheck` also runs `tsc -p server`, and the root `vitest` runs it as a second project (Node, not happy-dom).
- `npm run format` fixes Prettier; `npm test` = `vitest run` (happy-dom + WXT fake browser).
- One test file: `npx vitest run lib/credits.test.ts`; one test: add `-t "name"`.
- Server (Fripon Cloud, `server/`, its own `package.json` and lockfile): `npm --prefix server install` once, then `npm --prefix server run dev` (esbuild watch + `node --watch`, reads `server/.env`) / `build` -> `server/dist/main.js` / `start`. Its tests: `npm --prefix server test`, or `npx vitest run --project server`.
- Fripon Cloud deployment (VPS): `server/Dockerfile` (build context = repo root, see `.dockerignore`), `server/compose.yml`, `server/.env.example`, Caddy block in `server/caddy/fripon.caddy`; steps, backups and rollback in `docs/cloud.md`.

## Architecture

WXT 0.21 + Preact 11 + TypeScript strict (`noUncheckedIndexedAccess`), Manifest V3.

- `entrypoints/background.ts`: service worker. Answers `lib/messages.ts` requests (`analyzeImage`, `searchImage`, `aiReview`, `getGates`, `getVisionUsage` (credits left, a count only), `openOptions`, `setVerdictBadge`, `testKey`), opens the options page (toolbar button, first install). Handler logic is in `lib/background/handlers.ts`. `setVerdictBadge` (level + title of the card's verdict, or `null`) sets the toolbar badge of the sender's tab (`lib/background/badge.ts`: red `!`, orange `?`, green `✓`, tooltip « Fripon — <title> »); it is accepted only from a content script in a tab on an https Vinted page (`isVintedPageUrl`), never from an extension page, and only from the top frame of a real tab. The browser resets a tab's badge on navigation, so there is no `tabs` listener: the card sends the verdict from `show()` only when (level, title) changed, clears it in `dispose()`, and sends it again on a same-item `wxt:locationchange`.
- `entrypoints/listing.content.tsx`: content script on Vinted item pages. Mounts the card (shadow root UI), reads the listing, runs `lib/analysis.ts`, re-runs on bfcache restore and `wxt:locationchange`. The card shows from the free checks first; then one code path (`paidSteps`) runs the Vision search (automatic mode is a click nobody has to make) and `withImageSearch` redoes the verdict from the stored checks (no new Vinted request), then the AI review (`askAiReview`, with every signal including the Vision result) and `withAiReview` does the same. The page sends `searchImage` and `aiReview` whatever the gate; in "Au clic" mode it only sends `cacheOnly` by itself, and the one button starts both steps ("Lancer la recherche d'image", or "Lancer l'avis IA" when only Gemini is set up). The review always follows the image row: it is asked again (`aiReviewSteps`) whenever the search's result is not the one the last review was based on (`imageBasis`), e.g. a click after a cached review, or a retry that succeeds; the review also waits while the image row offers its retry button (a failed search that may pass), and a retry/click sends `retry` to skip the short failure memory; the search and the review have separate busy flags.
- `entrypoints/grid.content.tsx` + `ui/grid/` + `lib/grid/`: content script on every Vinted page except `/items/*` (`excludeMatches`), the « Analyser » button under each result card (catalogue, search, wardrobe, home feed). `ui/grid/controller.tsx` wires it: `injector.tsx` puts one shadow host (`fripon-grid-button`, all hosts adopt ONE constructed stylesheet, `<style>` fallback, `lib/grid/host.ts`) under each card's price (`findButtonAnchor`: the child of the text column that holds `--breakdown`, else `--price-text`, else `--description`), and a throttled (rAF) MutationObserver keeps them there (idempotent: infinite scroll, pagination, re-renders). The state is per item id in memory (`lib/grid/store.ts`: idle/running/done/needsKey/quota/error), so a re-rendered card shows its verdict again. A click runs `lib/grid/quick-analysis.ts`: `searchImage` (a real search, not `cacheOnly`) on the card thumbnail + `analyzeImage` for the local photos row, then `computeVerdict` (no seller, no description, price off) -> a compact verdict `{ level, title, line }` (« <Platform> · analyse rapide »). The photo is read again from the DOM at click time. The bar above the results (`GridBar.tsx`, placed by `findResultsAnchor` above the grid of the FIRST card) offers the cards in the viewport; a click takes the cards it offered (not a new measure), the batch is `asking` (credits requested) at once, never idle, so the bar cannot leave while it waits, and a bar with nothing in view only leaves after 1.5 s (`BAR_HIDE_DELAY_MS`): confirmation (« Jusqu'à N crédits Vision (il t'en reste M ce mois-ci) »), then `lib/grid/batch.ts` (pure queue, injected timers): one card at a time, 1 s apart, stops at the cap, without a key, after 3 failures in a row, or on « Arrêter ». The bar is hidden without a Vision key (`getGates`). The grid page never sends `aiReview` and never calls Vinted.
- `entrypoints/options/` + `ui/options/`: full-tab settings page (mode, keys, credits, guide). `ui/ListingCard.*`: the card.
- `lib/vinted/`: `listing-reader.ts` (JSON-LD + DOM), `selectors.ts` (every selector, one place), `anchor.ts`, `grid.ts` (result cards: `findCardRoots` + `readGridCard`, thumbnail rules, `findButtonAnchor`, `findResultsAnchor`), `domains.ts` (`VINTED_PAGE_MATCHES` for the grid script, `VINTED_ITEM_MATCHES` for the card), `api.ts` (seller fetch: shared request queue spaced 1.5 s across tabs, 24 h cache, cooldown after 403/429).
- `lib/checks/` (image, price, seller, photos, description) -> `lib/verdict.ts`; `lib/analysis.ts` orchestrates the free checks only (the paid steps are not part of it) and ends every step in one `assemble(rawChecks, aiReview)` (price row, AI confirmation, local-row cap, verdict), so image and AI compose in any order; an AI `catalogPhoto: true` makes the Photos row's `catalog_photo` signal strong only when an exact image match backs it, weak otherwise (`confirmCatalogPhoto`), so the AI alone never moves a verdict through a strong signal and never decides it; `lib/checks/image-matches.ts` turns Vision `pagesWithMatchingImages` into `ImageMatch[]` (platform allowlist by hostname, `exact` = full match on a product URL); `lib/image/` runs in the background: pixel hashing, `analyzer.ts` (guarded photo fetch, shared), `search.ts` (`searchImage`, cheapest step first: 7-day cache in `search-cache.ts` under `fripon:vision:v1:<origin+path>`, no key, 10-minute memo of a refused key, cap read without reserving, photo download, `reserve`, call; `refund` only when Google certainly did not bill).
- AI review: `lib/google/gemini.ts` (`reviewListing`, the paid call: model in `GEMINI_MODEL`, JSON mode, fenced answers stripped, strict validation, 30 s timeout), `lib/ai/input.ts` (what the page sends: photo URL, title, description, price, one plain French line per signal and a stable `fingerprint`, built from the raw rows; clamped in the background), `lib/ai/review.ts` (`createAiReviewer`, the `aiReview` handler, same steps as `search.ts`: cache, no key, key-failure memo, cap read, photo, `reserve`, call, `refund`), `lib/ai/review-cache.ts` (`fripon:ai:v1:<photo origin+path>:<hash of model, prompt version, title, price, fingerprint>`, 7 days), `lib/ai/block.ts` (the card's "L'avis de l'IA" states and failure lines).
- Shared by Vision and Gemini: `lib/google/refusal.ts` (`readRefusal`: the one place of the refund rule, `isKeyFailure`, and the `unavailable` failure for a 404/NOT_FOUND or, for Gemini, an unrecognised 400), `lib/google/failure-memo.ts` (a refused key is remembered 10 minutes, a quota, network or unavailable failure 90 seconds; a click sends `retry` and skips the short one), `lib/ttl-cache.ts` (7-day cache in `storage.local`, used by `search-cache.ts` and `review-cache.ts`), `lib/image/base64.ts`.
- `lib/settings.ts` (`fripon:settings:v1`), `lib/credits.ts` (counters `fripon:credits:v1:<provider>:<period>`, periods and resets on Pacific time like Google, caps from `CREDIT_POLICY`, atomic `reserve`/`refund`), `lib/lock.ts` (`navigator.locks` with an in-module fallback), `lib/gate.ts` (one gate per paid step, `ready|no_key|quota|manual`: `getGates` answers `{ image, ai }`), `lib/google/key-check.ts` (free key test, and the Google error classifier `refusal.ts` reuses), `lib/google/vision.ts` (`webDetect`, the paid WEB_DETECTION call), `lib/options-nav.ts` (which options section to show, via `storage.session`), `lib/background/client.ts` (what a page asks of the background: `searchDeps`, `askGates`, `askVisionRemaining`, `openOptions`, `setVerdictBadge`; shared by the card and the grid).
- Fripon Cloud, subscriber mode (`lib/cloud/`, server in `server/`): signed in (a session in `storage.local`), the two paid steps go to the Fripon server instead of the user's keys; signed out, nothing changes. `config.ts` (`CLOUD_ORIGIN`, the one place the server is named: `client.ts` and the manifest's host permissions read it), `session.ts` (`fripon:cloud:v1` `{ token, email }`, or `{ expired: true, email }` once the server refused the token: `expireSession`, no token; `sessionState()` = `signed_in | expired | signed_out`; the options page reads only the marker, through `loadExpired`; `fripon:cloud:status:v1` = the status without the token, written and removed together with the session, what the options page follows through `useStored`), `client.ts` (typed fetch wrapper, 45 s search/review (the server's photo 10 s + Vision 20 s or Gemini 30 s), 10 s the rest, never rejects, a 401 expires the session, `DELETE /v1/account` for the account deletion), `types.ts` (a copy of the server's `usageSummary`, parsed), `status.ts` (`createStatusKeeper`: `/v1/me` at most once a minute, a failed read counts, the last snapshot is kept offline; `cloudGate`/`cloudRemaining`/`createCloudGates` = `getGates` and `getVisionUsage` while signed in; a usage never read is `ready`/`manual`, never `no_key`; a 401 while reading it is `expired`), `steps.ts` (`searchImage`/`aiReview` with the same contract as the key-based ones: local caches first (the same ones), `cacheOnly` never goes further, a 90 s memory of failures, in-flight dedupe; the server decides the cap, never the stored status (it serves a photo already analysed this month for free, even at the cap): only a photo the server just refused (402) gets `quota` locally for 60 s, per photo and account, which also spares the search 402, review 403, search 402 chain of one listing; a click's `retry` skips it; the review's `quota` carries `source: 'cloud'`, so the AI block says « Tu n'as plus d'analyses disponibles. » and leads to the `cloud` section; the local caches are shared by every account of the browser, on purpose), `account.ts` (what the options page asks: sign-in (ends the session it replaces at the server, best effort), status, sign-out, Checkout/portal opened in a tab from the background, `deleteAccount` (204 clears the session; 409 `active_subscription` keeps it)), `router.ts` (`createRouter` picks cloud or personal at every call from the session state: an expired session works from the personal keys but says `expired` where a step would say `no_key` (gates and answers), so the card asks to sign in again and never for a Google key; `sectionFor` sends the card's guide/keys/credits buttons to the `cloud` section when signed in or expired). The `cloud*` messages are extension-page only (`EXTENSION_PAGE_ONLY`, like `testKey`). `ui/options/CloudSection.tsx` is the « Abonnement Fripon » section.

- `server/`: Fripon Cloud, the subscription server (Node + Hono + better-sqlite3, ESM, bundled by esbuild so it can import `../lib`). `src/config.ts` (env, validated once; add a variable = one line), `db.ts` (schema in `MIGRATIONS`, versioned by `PRAGMA user_version`; every timestamp is epoch ms), `time.ts` (`periodIds`: month and day on the Paris calendar), `plans.ts` (`PLANS` by Stripe price lookup key, `entitlement`), `quota.ts` (`reserveAnalysis`/`release`, `allowReview`/`releaseReview`, `usageSummary`: the only code that decides what an analysis costs, each write one `BEGIN IMMEDIATE` transaction), `auth.ts` (e-mail code -> bearer token; codes are HMACs, tokens are SHA-256 at rest, 3 sessions per account), `mailer.ts`, `rate-limit.ts`, `context.ts` + `app.ts` + `routes/` (`createApp(deps, extraRoutes)`: other route groups are `RouteModule`s, `ctx.requireAccount` is the auth + per-account limit middleware). No CORS headers on purpose, JSON bodies only, 16 KB max. Tests sit next to the code; `test-helpers.ts` has the in-memory db, fake clock and mailer.
- Server billing (`routes/billing.ts`, `stripe.ts`, `stripe-setup.ts`): the Stripe webhook is the only writer of `plan`/`subscription_status`/`period_end`, and every event reduces to "read the subscription again from Stripe, store it" (never trust the payload or the order of events). `StripeApi` is the injectable surface (tests sign real payloads with `generateTestHeaderString`); the API version is the SDK's own (`STRIPE_API_VERSION`); prices are found by the lookup keys of `plans.ts`. `npm --prefix server run stripe:setup [-- --webhook <https url>]` creates product, prices, portal and webhook (idempotent, refuses a live key without `--live`; reads `STRIPE_SECRET_KEY`). The webhook route takes 256 KB, every other route 16 KB.
- `safari/Fripon/`: Xcode project (container app + Safari extension target, bundle id `fr.fripon.Fripon`), generated once by `safari-web-extension-converter` and committed. `Fripon Extension/Resources/` is an ignored copy of the WXT build (`scripts/safari-sync.mjs`); `scripts/safari-app.mjs` runs `xcodebuild`. ESLint and Prettier skip `safari/`.

## Conventions

- Code, identifiers, comments, commit messages in English. User-facing UI text in French (tutoiement).
- No GitHub Actions, ever (owner's rule). Gates run locally.
- Never commit API keys or `.env` files. BYOK keys live in extension storage only.

## Pitfalls

- Vinted's API needs the header `accept: application/json`, or Cloudflare answers 403 with a challenge page.
- `/api/v2/items/<id>/details` always returns 403: item data comes from JSON-LD + DOM (`listing-reader.ts`).
- Hashed CSS classes change on every Vinted deploy: only `data-testid` and `details-list--*` are stable.
- API keys are only read in the background (and shown on the options page). Content scripts get a gate word, never a key; `testKey` is accepted from extension pages only. Keys go in the `x-goog-api-key` header, never in a URL.
- A Gemini key must come from a Google Cloud project without billing: billing switches Gemini to the paid tier. Vision needs billing, so the two keys need two projects.
- Vinted is not a single-page app (pages reload), but bfcache restores (`pageshow`) and `wxt:locationchange` are handled anyway.
- Paid Google calls (lots 3-4): `reserve` a credit in the background right before each call and `refund` it if the call cost nothing. The gate sent to pages is only a display hint.
- Do not touch existing storage keys (`fripon:seller:v2:*`, `fripon:lastRequestAt:*`, `fripon:cooldownUntil:*`).
- Vinted re-renders the item sidebar ~0.3 s and ~2 s after load: injected nodes must re-attach, and browser tests must inject at DOMContentLoaded, not after load.
- Vision WEB_DETECTION finds Shein catalog photos as many `pagesWithMatchingImages` across shein country hosts (some are category pages): exact = `fullMatchingImages` on a product URL.
- Listing-grid thumbnails often lazy-load placeholders: take `og:image` / JSON-LD photos instead.
- Typed `browser.runtime.getURL('/options.html')` only exists after `wxt prepare`: build the URL from `getURL('/')`.
- Gemini model: only `gemini-flash-lite-latest` works on the free tier (5-7 s, ~1 300 tokens per review). `gemini-3.8-flash` times out or answers 503, `gemini-2.5-flash` is a 404. The model is the single constant `GEMINI_MODEL`; a 503 or a timeout is a non-refundable network failure.
- The original price cannot be read with free keys: Shein serves an anti-bot page, Gemini `url_context` reads the page without any price, and Google Search grounding is not in the free tier (quota 0). Do not build price comparison on it: the price row stays "Non comparé" and the verdict uses no price ratio.
- Gemini answers in JSON mode can still come wrapped in a ```json fence: strip it before parsing, then validate strictly (boolean `catalogPhoto`, non-empty `summary` of at most 600 characters, HTML stripped). Anything else is `invalid_answer`, and the credit stays spent.
- The AI review's signal lines and fingerprint are built from `rawChecks` (never from the AI-confirmed row, or the review would feed on its own answer). The cache key hashes the fingerprint (the image line, then `id:status:tag` of each row) and not the lines, whose counts ("N avis") move between visits; change `PROMPT_VERSION` when the prompt changes.
- `catalogPhoto` is asked first and judged on the photo alone (the prompt says so); the signals only serve the summary. Do not let a check's result tilt it.
- Titles and descriptions are the seller's words: the Gemini prompt puts each on one line, quoted with JSON rules (a forged "Indices calculés par Fripon" block cannot start a line of its own) and tells the model they are text to summarise, never instructions. The AI only ever confirms a signal and writes a summary.
- A free-tier Gemini key lets Google use what is sent (photo, title, description, price, signal lines): the options page and the guide say so (all of it, price and signals included). Keep them in step if the review ever sends more.
- Subscriber mode sends the photo address, title, description, price and signal lines to the Fripon server, which calls Google with its own paid key: `CLOUD_PRIVACY` (`CloudSection.tsx`, shown in the section and in the guide) also says what the server keeps (e-mail, subscription state, analysed photos 2 months at most, results 35 days for photos and 7 for reviews, IP addresses only hashed), who else is involved (Google, Stripe, an e-mail service, a host: none named, none decided) and that the account can be deleted from the page; the options footer, the keys section and the README say so too, for both modes. Keep them in step.
- In subscriber mode no failure word of a key (`invalid`, `restricted`, `disabled`, `billing`) may reach a page: the card would send the user to check a key they do not have. `steps.ts` maps a server failure to `network`, `unavailable` or `photo` only (a 429 reads as `network`), a 402 to `quota`, a 401 to `expired` (the session is already marked expired; `no_key` is only for no session at all). A `review` never answers 402: the client reads it as `unavailable`.
- The server reviews only a photo it served to the account lately (`403 not_searched`). A search answered by this browser's cache (made before signing in, or by another account) was never served by it: `steps.ts` then has the server serve the photo (one analysis) and asks the review again, once.
- Signed in means cloud only, with no fallback to the user's keys. The router looks at the session at every call, so a sign-in or sign-out takes effect at the next request. The status snapshot is a display hint like any gate: the server is the only judge of a cap, `steps.ts` never refuses a request from a stored status. The expired marker goes away on a sign-in, a sign-out, or when a Google key is saved (the background's `storage.onChanged`, `clearExpired`).
- A stored Gemini cap of 20 (the old default, written by every save) is read as the new default of 100; a deliberate 20 a day cannot be chosen.
- Safari may kill the service worker between `reserve` and the cache write: the credit is lost and the in-flight dedupe is gone. Accepted.
- Safari: the Xcode project lists each top-level entry of the extension (files one by one, folders as references), so a new top-level file in the build (new HTML entrypoint...) makes `safari:sync` fail until the project is regenerated (`docs/safari.md`, "Régénérer le projet Xcode"); hashed files inside `chunks/`, `assets/`, `content-scripts/` are fine. The converter also rewrites the container app text and sets the deployment target to the host macOS: see `docs/safari.md`.
- Safari: no Apple Developer account, so builds are ad-hoc signed and need Develop > "Allow Unsigned Extensions", which Safari resets at every restart. Safari asks the user to allow each site (vinted.*, `*.vinted.net`, Google APIs): without it the card does not show or the photo fetch fails. Safari suspends the service worker quickly: in-memory caches (analyzer, refused-key memo) are only optimisations, anything that must survive lives in `storage.local`.
- Result cards (recon 2026-10-27): the root is `product-item-id-<id>` (catalogue, search, wardrobe) or `feed-item` (home feed, id only in the link); its parts share the prefix (`--image--img`, `--overlay-link`, `--summary` > `--description` (`--description-title`, `--description-subtitle`), `--price-text`, `--breakdown`), so only an exact match is a card and a card without `--description` (promotions, being drawn) is skipped. Parts are found by testid suffix inside the root.
- A link (`--overlay-link`) covers the whole card: the Fripon host must be `position: relative` with a z-index above it (inline `!important`), and every click on it does `preventDefault` + `stopPropagation` (the compact verdict is the one real link, to the item page, it only stops propagation).
- The home feed replaces its `main` ~0.4 s after load and the catalogue is paginated (96 cards a page): never inject once, always re-scan; hosts are keyed on the card element (WeakMap), views on the item id.
- Content scripts cannot define custom elements: `fripon-grid-button` / `fripon-grid-bar` are plain undefined tags with a shadow root. A constructed stylesheet made in the content script may be refused by a page's shadow root (Firefox): the `<style>` fallback is part of the design.
- Grid thumbnails: `https` + `*.vinted.net` only, never a `data:` placeholder, never a 100 px thumbnail (`/100x100/`, `/70x100/`): without a usable photo the card says « Recherche impossible » and sends nothing.
- A batch counts cards in the viewport (`getBoundingClientRect`, any overlap) at the click on the bar; the list is frozen for the confirmation. happy-dom lays nothing out, tests inject `isShown`.
- Keyboard focus in the grid blocks: a redraw swaps controls (button -> verdict link, « Analyser » -> « Lancer »), so `redrawKeepingFocus` (lib/grid/host.ts) gives the focus to the new control when the old one had it, and `moveKeepingFocus` does the same for a host that is moved (`after`/`before` drops the focus). Every programmatic focus goes through `focusInPlace` (`preventScroll: true`: the page must never jump) and only when the focus was in our UI right before. Ask `document.activeElement === host` (the host while a control of its shadow tree is focused), never `shadowRoot.activeElement` of every host: happy-dom's getter throws when the focus is in another shadow root.
